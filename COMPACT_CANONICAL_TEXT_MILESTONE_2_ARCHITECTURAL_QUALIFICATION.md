# Compact canonical text: production integration qualification

20 November 2026. Experimental qualification only; no production migration is approved or implemented. Read alongside `COMPACT_CANONICAL_TEXT_MILESTONE_2_IMPLEMENTATION.md` and the accepted first proof.

## Decision boundary

Compact text cannot be installed as a drop-in `CanonicalRepository` adapter. Production `ContentRecord.inlineContent` contains placement keys; commands, projection, native capture, ownership and exact history interpret those keys as canonical records. Returning editing keys through that interface would create an invalid second authority. The experiment instead keeps compact native Blocks authoritative and creates disposable Cells per mounted occurrence. Its nominal service casts mark unqualified interfaces, not production compatibility.

The narrow next step is a separately approved repository/command contract spike, with legacy and compact content explicitly distinguished in memory. Do not remove production Cell occurrences or change persisted wire/history schemas as a side effect. Keep current repository operation and replay intact until every consumer below is qualified.

## Inline objects and standoff affinity

`TreeCommands.insertInlineImage` inserts a typed canonical image and increments host revisions without transforming the host's standoff properties. Ordinary `replaceInlineRange` does transform them. The experiment characterizes that difference and compares image insertion against one-character insertion at five boundary positions; it does not patch production commands.

Recommended future policy: every *new* logical inline replacement passes through the same range transform, counting each typed object as one position. A collapsed insertion uses the current text-insertion boundary rules, including explicit point affinity. Both accepted zero-width forms move/delete equivalently but retain their original endpoint difference. Replacement deletion/insertion must be one operation, not sequential rebases. Keep image payload, asset references and definition ownership intact.

Audit `insertInlineImage`, inline move/copy, clipboard typed paste, cross-Block replacement, structural split/join and exact operation recording together. Existing documents may have annotations authored around the old image behavior; old history already records concrete payloads. Replaying it under a new transform would corrupt historical meaning. Therefore a production change requires separate compatibility qualification and approval; the experimental preference alone is insufficient.

## Architecture options

1. **Explicit compact capability in the existing repository (recommended investigation).** Share transaction, ownership, resource and dirty-state machinery; introduce typed sequence command/projection ports. Advantages: one authority, existing resource lifecycle. Cost: a real representation change across the boundaries above, with legacy paths retained.
2. **Production repository replacement.** Broad rewrite of validation, history, projection and applications. The milestone supplies insufficient evidence and no authorization for this option.
3. **Read-only integration first.** Reuse compact styled runs for previews without replacing production interactive storage. This is independent of editing qualification; retain the accepted subset and clearly mark unsupported visuals. It does not solve production interactive admission.

No complete Cell-record facade, new general-purpose gateway, renderer, geometry cache, rope, piece table, virtualization framework or persisted point-policy flag is justified by this milestone.

## Next approval-sized experiment

First implement and test a detached compact write-set planner against production validation and history contracts, without changing the active application repository. Differentially compare text/object replacement, annotations, split/join and exact replay. Then qualify one production mounted occurrence through explicit ports, including clipboard, managed assets, annotation identity and two-view history. Keep legacy history/native fixtures and the full Flint lifecycle as release gates. Resource admission and application rollout require their own evidence; prototype latency alone cannot clear the existing production blocker.
