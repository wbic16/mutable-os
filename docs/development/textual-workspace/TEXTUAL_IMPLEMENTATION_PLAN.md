# Textual implementation plan

**Current direction: four increments; accepted investigation is the baseline.** This plan supersedes the previous eight stages and exhaustive requalification proposals. Do not repeat the source audit or regenerate inventories. Share the engine, separate the views, preserve existing behaviour.

**Progress:** Increment 1 shell foundation is implemented; see its [concise qualification](TEXTUAL_INCREMENT_1_QUALIFICATION.md). Dedicated Flint hosting and tool views remain in increments 2 and 3.

## Isolation boundaries

- Dedicated Textual shell, Flint chrome, menus, dialogs, inspectors, Scry/LER, Gloss/References and Cardex views. Existing graphical views retain their layout, markup, defaults and styles.
- Reuse commands, service/controller state, document sessions, native editor DOM, Block renderers, selection/IME, history and persistence. Do not mount a second editor or duplicate validation/mutation logic.
- Where behavior lives inside JSX or imperative UI code, extract only the needed operation/state into a presentation-neutral port. The original view consumes that port with its existing defaults; it does not acquire Textual layout branches. Prefer an existing service over extraction.
- Select presentation factories at application/overlay composition boundaries. Shared services do not import Textual components. Textual-only entry choices, such as Query-first Scry, do not change graphical defaults.
- Scope styles, tokens, font metrics and geometry to Textual roots, including owned portals. No global resets, body/root font changes or graphical stylesheet rewrites. Restore the original presentation context on retained editor transfer. Native island internals remain native.
- Keep stateful controller/editor owners alive independently of replaceable chrome. Mount a retained editor in one host at a time. Composition, pending saves, dialogs and draft decisions keep their existing lifecycle guards.

Source inspection identifies the needed boundaries: `DocumentApplicationInstance` already exposes Flint operations, but its host mixes tab rendering and services; LER retains operations in `ler-view.tsx`; Gloss builds its input DOM in `controller.ts`; Cardex owns form state in its views. Those are bounded extraction candidates, not grounds for general refactoring. Their concrete contracts are qualified when the affected increment reaches them. Do not implement a boundary whose ownership or rollback remains unresolved.

## Testing and reporting discipline

For each increment, test new code and changed integration boundaries, then stop once focused checks pass. Reuse existing regression tests for unchanged operations. Do not perform a new inventory audit, exhaustive platform/Unicode matrix or unrelated accessibility/performance campaign. Pursue unusual Unicode/scaling cases only when a concrete defect or data/editing risk justifies it. Keep semantic controls and effective shortcuts correct as part of implementation.

Critical checks: measured character-cell layout/zoom; existing Flint functionality; unchanged graphical Workspaces; accessible functional Scry/Gloss/References/Cardex; no unnecessary editor remounts, repository snapshots or expensive typing/switching work. Compare scoped counters and representative browser interaction, not arbitrary frame settling. Preserve a cheap before/after graphical fixture for every shared boundary; screenshots alone do not prove editing/lifecycle correctness.

Each qualification note contains only changed files/register IDs, tests and results, outstanding issues and next action. Feature-flag rollback must preserve canonical data and graphical preferences. Do not lower old assertions or update graphical snapshots to conceal a regression. Escalate a concrete ownership/caret/persistence blocker; do not expand the investigation speculatively.
